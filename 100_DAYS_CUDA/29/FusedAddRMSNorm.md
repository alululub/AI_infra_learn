# Day 29 · Fused Residual Add + RMSNorm

Day 28 把输入 `x` 保存在寄存器里，算完一行的平方和，再用寄存器里的 `x` 写出归一化结果。Day 29 把这条思路前移一步。线程先算出自己的 `h = x + residual`，用 `h` 累加平方和，等整行的缩放因子算出来后，再从寄存器取出 `h`，写回残差和归一化结果。 [Day 28 学习文档](../28/RMSNorm.md) · [Day 29 CUDA 源码](FusedAddRMSNorm.cu)

## 1. 输入、输出和数学定义

把输入张量展平为 `M × N`。`M` 是 token 行数，`N` 是每个 token 的 hidden 特征数。本实验使用连续 FP32 缓冲区。

| 变量 | 形状 | 含义 |
| --- | --- | --- |
| `x` | `[M, N]` | 当前子层的输出 |
| `residual` | `[M, N]` | 残差支路传来的值 |
| `gamma` | `[N]` | 各列的缩放权重，所有行共享 |
| `h` | `[M, N]` | 两个输入的逐元素和，供后续残差路径使用 |
| `y` | `[M, N]` | 对 `h` 沿 hidden 维做 RMSNorm 的输出 |

对第 $r$ 行第 $c$ 列，先计算 $h_{r,c}$，再用整行的 $h$ 算出同一个 `inv_rms`。

$$
h_{r,c} = x_{r,c} + \mathrm{residual}_{r,c}
$$

$$
\mathrm{inv\_rms}_r = \frac{1}{\sqrt{\frac{1}{N}\sum_{c=0}^{N-1} h_{r,c}^{2} + \varepsilon}},
\qquad
y_{r,c} = h_{r,c} \cdot \mathrm{inv\_rms}_r \cdot \gamma_c
$$

`inv_rms` 每行一个，`gamma[col]` 每列一个。`h` 和 `y` 分别写到独立的输出缓冲区，这样两种实现可以用同一份 `x` 和 `residual` 反复测试。

### 用四列手算一行

| 列号 | 0 | 1 | 2 | 3 |
| --- | ---: | ---: | ---: | ---: |
| `x` | 1 | 1 | 2 | −3 |
| `residual` | −1 | 2 | 2 | 3 |
| `h` | 0 | 3 | 4 | 0 |
| `h²` | 0 | 9 | 16 | 0 |
| `gamma` | 1 | 0.5 | −2 | 1.5 |

平方和是 `25`，除以真实列数 `4` 得到 `6.25`。加上 `eps = 1e-6` 再取平方根的倒数，`inv_rms` 约等于 `0.4`。

```text
y[0] = 0 × 0.4 × 1    ≈  0
y[1] = 3 × 0.4 × 0.5  ≈  0.6
y[2] = 4 × 0.4 × (-2) ≈ -3.2
y[3] = 0 × 0.4 × 1.5  ≈  0
```

源码的 `2 × 4` 用例用这一行做测试。第二行让两路输入完全抵消，检查全零行也能得到有限结果。此时分母是 `sqrt(eps)`，所以 `0 * inv_rms` 仍为 `0`。 [测试输入](FusedAddRMSNorm.cu#L381)

## 2. 未融合基线和融合版

| 路径 | 第一次 kernel 启动 | 第二次 kernel 启动 |
| --- | --- | --- |
| 未融合 | `residualAddKernel` 读 `x` 和 `residual`，写 `h` | RMSNorm 读 `h` 和 `gamma`，写 `y` |
| 融合 | 读 `x` 和 `residual`，在同一个 kernel 中计算并写 `h` 和 `y` | 无 |

未融合的加法对各元素独立，可以把矩阵当作一维数组。线程从 `blockIdx.x * blockDim.x + threadIdx.x` 开始，每次前进整个 grid 的线程数。总元素数能被 4 整除时，线程以 `float4` 为单位相加。 [加法 kernel](FusedAddRMSNorm.cu#L94)

两条路径共用同一份 RMSNorm 模板。`FUSE_ADD=false` 的 `input` 指向已经算好的 `h`。`FUSE_ADD=true` 的 `input` 指向 `x`，模板里的 `if constexpr` 让编译器只在融合版保留读取 `residual` 和写 `h` 的代码。比较两个向量版本时，线程分组、归约方式和归一化公式一致。 [模板实现与分派](FusedAddRMSNorm.cu#L161)

## 3. 跟着一个 block 读融合 kernel

### 第一步 · 一个 block 管一行

`blockIdx.x` 是行号，`row_start = blockIdx.x * N` 是这行在一维数组里的起点。固定启动 256 个线程。向量版把行再看成 `N / 4` 个 `float4`，第 `tid` 个线程第 `k` 轮负责 `idx = tid + k * 256` 这一组。

例如 `N = 4096` 时，一行有 `1024` 组，每线程负责 4 组，调用 `rmsNormVec4Kernel<4, true>`。线程 1 的 `idx` 依次为 `1、257、513、769`。第 `257` 组从标量列 `4 × 257 = 1028` 开始，覆盖 `1028–1031`。这里 `float4` 的 `4` 是每组的列数，模板参数 `<4, true>` 中的 `4` 是每线程的组数。

### 第二步 · 读两路输入，保存逐元素和

每个有效 `idx` 各从 `x` 和 `residual` 读四个值。`add_values()` 对四个分量分别相加，把结果放进当前线程自己的 `values[k]`。这份数组跨过后面的归约，还会在写回阶段使用。数组大小是编译期常量，展开循环后编译器可以为各分量分配寄存器。 [加载循环](FusedAddRMSNorm.cu#L187)

### 第三步 · 求本行的缩放因子

每个线程先用 `fmaf(value, value, sumsq)` 把自己的元素平方累加起来，再调用 `block_reduce_sum()` 合并。每个 warp 用 5 轮 XOR shuffle 得到局部和，lane 0 写入共享内存。一次 `__syncthreads()` 等 8 个局部和都就绪。接着每个 warp 的 lane 0–7 读取这 8 个数，其余 lane 提供 0，再做一遍 warp 归约。这样每个线程都拿到整行 `sumsq`，可以自行计算 `rsqrtf(sumsq / N + eps)`。 [单次 block 同步的归约](FusedAddRMSNorm.cu#L58)

### 第四步 · 用同一份 `h` 写两个结果

线程从自己的 `values[k]` 取出 `h`，一次写给残差输出，一次乘上 `inv_rms` 和四列各自的 `gamma` 后写给 `y`。归约交换的是平方和，`h` 仍由原来的线程写回。向量融合版因此省掉了 RMSNorm 从全局内存重新读取 `h` 的那一步。 [写回循环](FusedAddRMSNorm.cu#L218)

## 4. 模板档、空位和标量回退

向量路径需要 `N % 4 == 0` 来保持各行起点的 `float4` 对齐。本实验的缓冲区直接用 `cudaMalloc` 分配。Host 端计算 `ceil((N / 4) / 256)`，从 `1、2、4、8` 中选择能放下所需组数的最小模板档。 [Host 分派代码](FusedAddRMSNorm.cu#L252)

| 行宽 `N` | 每行 `float4` 组数 | RMSNorm 路径 | 原因 |
| ---: | ---: | --- | --- |
| 100 | 25 | `vec4<1>` | 线程 0–24 各处理一组，其余线程以 0 参与归约 |
| 1001 | — | 标量 | 每行的起点无法统一保持 16 字节对齐 |
| 2048 | 512 | `vec4<2>` | 每线程 2 组 |
| 4096 | 1024 | `vec4<4>` | 每线程 4 组 |
| 5120 | 1280 | `vec4<8>` | 每线程需要 5 组，向上选到 8 |
| 8196 | 2049 | 标量 | 需要 9 组，超过最大模板档 |

`N = 5120` 的后三个槽会填 0，写回时只写 `idx < N / 4` 的组。求均方时的分母是 `5120`。所有线程都要走到归约与同步，因此空槽也保留了线程的参与。

标量融合版先按 `col = tid + k * 256` 遍历输入，写出 `h` 的同时累加平方和。归约后，它读取自己刚才写的列并计算 `y`。这个版本也把两步放进一次 launch，借助全局内存保存宽行或非对齐行的 `h`。 [标量回退](FusedAddRMSNorm.cu#L114)

## 5. 理论访存量与寄存器代价

设一块 FP32 矩阵的大小为 `B = M * N * sizeof(float)`。下表只数向量路径对四块矩阵的逻辑读写量，`gamma` 由每行按列读取，两版都需要它。实际 DRAM 流量还受缓存影响。

| 矩阵访问 | 未融合 | 融合 |
| --- | ---: | ---: |
| 读 `x` | `B` | `B` |
| 读 `residual` | `B` | `B` |
| 写 `h` | `B` | `B` |
| 读 `h` | `B` | 0 |
| 写 `y` | `B` | `B` |
| 合计 | `5B` | `4B` |

以 `1024 × 4096` 为例，`B = 16 MiB`。向量版融合后省去 `16 MiB` 的逻辑读，总量从 `80 MiB` 减到 `64 MiB`。若两版达到同样的有效传输速率，且搬运时间占主导，`5 ÷ 4 = 1.25` 可以作为估算。实际测试还包含 launch、计算和资源占用的影响。

`nvcc 11.8` 为 `sm_86` 编译时，`ptxas` 给出的寄存器数量如下。两列的向量实例都报告了 0 字节 stack frame 和 0 字节 spill。

| 模板档 | 未融合的 RMSNorm 寄存器/线程 | 融合版寄存器/线程 |
| --- | ---: | ---: |
| `vec4<1>` | 19 | 20 |
| `vec4<2>` | 26 | 26 |
| `vec4<4>` | 39 | 44 |
| `vec4<8>` | 48 | 58 |

融合版节省一次矩阵读，同时在 kernel 内处理两份输入并写两份结果。寄存器数升高时，每个 SM 能同时驻留的 block 可能变少，因此需要结合具体形状判断效果。

## 6. 编译、正确性和 CUDA Event 计时

在仓库根目录执行以下命令。`sm_86` 对应本次使用的 RTX 3060 Laptop GPU，使用其他 GPU 时按对应计算能力选择编译目标。

```bash
cd 100_DAYS_CUDA/29
nvcc -std=c++17 -O3 -arch=sm_86 -lineinfo -Xptxas=-v FusedAddRMSNorm.cu -o FusedAddRMSNorm
./FusedAddRMSNorm
```

`run_case()` 用固定种子的 `rng` 生成 CPU 输入。两路输入用 `normal(rng)` 逐项填入，`gamma` 用 `[0.5, 1.5)` 的均匀分布生成。前面手算的 `2 × 4` 用例换成了指定的输入和权重。输入复制到 GPU 后，两条路径各执行一次正确性检查。

CPU 先以 FP32 计算参考 `h`，保持和 GPU 存储 `h` 一致的舍入位置。然后用 `double` 累加 `h²`，求逆 RMS 并计算参考 `y`。`h` 要求数值相等，`y` 按 `abs_err <= 2e-6 + 2e-6 * abs(y_ref)` 逐元素检查。检查前把两个输出缓冲区都填成 NaN，可让任何漏写的元素在校验时暴露。 [CPU 参考与比较](FusedAddRMSNorm.cu#L292)

性能测试每条路径预热 10 次，再用 CUDA Event 计 200 次取平均。未融合的一次迭代计入加法和 RMSNorm 两个 kernel。两版的 `GB/s effective` 统一用 `4B ÷ 耗时` 计算，方便比较相同输入输出的处理速度。 [计时代码](FusedAddRMSNorm.cu#L334)

本机 11 组用例的两条路径均通过，`h` 最大绝对误差为 `0`，`y` 最大绝对误差为 `1.05e-6`。以下是同一次运行里几个代表性形状。 [完整运行日志](run_log.txt)

| `M × N` | RMSNorm 路径 | 未融合 / µs | 融合 / µs | 加速比 |
| --- | --- | ---: | ---: | ---: |
| `512 × 100` | `vec4<1>` | 6.65 | 4.34 | 1.53× |
| `512 × 1001` | 标量 | 36.57 | 29.43 | 1.24× |
| `1024 × 1024` | `vec4<1>` | 84.36 | 60.03 | 1.41× |
| `1024 × 2048` | `vec4<2>` | 160.76 | 121.53 | 1.32× |
| `1024 × 4096` | `vec4<4>` | 309.02 | 249.94 | 1.24× |
| `1024 × 5120` | `vec4<8>` | 394.65 | 310.10 | 1.27× |
| `4096 × 4096` | `vec4<4>` | 1220.25 | 970.20 | 1.26× |
| `32 × 8196` | 标量 | 18.42 | 21.30 | 0.86× |

`32 × 8196` 是宽行的标量回退，在这次测量里融合后反而更慢。对于这组形状，融合版仍会重读 `h`，而且只有 32 个 block，每个 block 要处理很长的一行。上面的 `5B` 到 `4B` 估算适用于向量路径。

## 7. Nsight Compute 实测

```bash
ncu --set full -o ncu_log_repro ./FusedAddRMSNorm --ncu
```

`--ncu` 固定运行 `1024 × 4096`，未融合路径提交加法和 RMSNorm 两个 kernel，融合路径提交一个。报告中的 `rmsNormVec4Kernel<4, 0>` 对应未融合的归一化阶段，`rmsNormVec4Kernel<4, 1>` 对应融合版。原始采集保存在本目录的 `ncu_log.ncu-rep`。仓库的 `.gitignore` 会忽略 `.ncu-rep` 文件，以下数据可以直接对照复现。

| Kernel 或路径 | 耗时 / µs | DRAM 读 / MB | DRAM 写 / MB | DRAM 合计 / MB |
| --- | ---: | ---: | ---: | ---: |
| 未融合 · 加法 | 159.328 | 33.567 | 16.494 | 50.061 |
| 未融合 · RMSNorm | 106.144 | 16.819 | 16.136 | 32.955 |
| 未融合 · 两次启动合计 | 265.472 | 50.386 | 32.630 | 83.016 |
| 融合 | 211.616 | 33.615 | 33.355 | 66.970 |

融合后总 DRAM 流量约减少 `16.05 MB`。流量比 `83.016 / 66.970 ≈ 1.24`，与 kernel 耗时比 `265.472 / 211.616 ≈ 1.25` 接近，说明少搬一次 `h` 是这组形状快下来的主要因素。这里的 `MB` 是十进制单位，前面的 `MiB` 是以 1024 为进位的单位。上一节的 Event 测量对整条路径反复计时，本节取 Nsight Compute 分别测得的单个 kernel 时长。

## 8. 自测题

1. **为什么融合版仍然要写 `h`？**<br>这里的接口同时返回残差结果和归一化结果。`h` 可以交给后续残差路径，当前 kernel 从寄存器复用同一份值计算 `y`。
2. **`N = 4096` 时，线程 1 的第二个 `float4` 覆盖哪些列？**<br>`idx = 1 + 256 = 257`，所以 `col = 4 × 257` 开始，范围是 `1028–1031`。
3. **`N = 5120` 选 `vec4<8>` 后，平方和要除以多少？**<br>除以 `5120`。多出的三个槽填 0，它们没有增加有效元素数。
4. **归约的 `__syncthreads()` 在等什么？**<br>等 8 个 warp 的 lane 0 写完各自的局部平方和。之后每个 warp 都能读齐这 8 个部分和。
5. **两个 `float4` 版本各读写几份矩阵？**<br>未融合路径读 `x`、`residual`、`h`，写 `h`、`y`。融合路径读 `x`、`residual`，写 `h`、`y`，中间计算所需的 `h` 从寄存器取。
